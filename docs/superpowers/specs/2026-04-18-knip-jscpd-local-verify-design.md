# Knip／jscpd によるローカル品質チェック（設計）

作成日: 2026-04-18  
対象: `kazkiueda-com`（Astro 6・Bun・TypeScript・Tailwind v4）  
合意内容: brainstorming セッションでの Kazki の承認を反映

## 1. 目的と境界

### 1.1 目的

次の両方を満たす。

- **未使用コードの検出（A）**: 未使用に近い依存関係・エクスポート・ファイルなどを機械的に洗い出す。
- **重複・類似コードの検出（B）**: ソース内の類似／重複ブロックを検出し、リファクタや意図の確認につなげる。

### 1.2 運用上の境界

- **ローカル限定**: push 前など、開発者が自分の環境で実行する。
- **CI でのゲート化はしない**: この仕様ではリモート CI を赤くしない。
- **pre-push フックは当面入れない**: 必要になれば後から、本仕様で定義した集約コマンドをフックから呼ぶだけで足せる状態にする。

### 1.3 スコープ外

- SonarQube のようなサーバ常設の品質ダッシュボード一式。
- CI 強制または必須の Git フック自動セットアップ。

## 2. ツール選定と役割

### 2.1 選定結果

| ニーズ | ツール | 役割 |
|--------|--------|------|
| A（未使用） | **Knip** | 依存・エクスポート・ファイルなどの未使用検出 |
| B（重複／類似） | **jscpd** | トークンベースの複製／類似ブロック検出 |

両ツールとも **devDependency** とし、**Bun** で実行する（`package.json` の `packageManager` に合わせる）。

### 2.2 選定理由（要約）

- 「未使用」と「重複」は失敗パターンが異なるため、**用途に特化したツールを組み合わせる**方が設定と運用が明確になる。
- ESLint を新規に敷いて重複まで含める案は、このリポジトリの現状（ESLint 未導入）では**導入コストが目的に対して大きい**ため採用しない。

## 3. 設定方針

### 3.1 Knip

- ルートに **Knip 用の設定ファイルを 1 本**置く（形式は導入時点の公式推奨に従う）。
- **最小から開始**: 最初は広い除外を書かず、レポートを見ながら **誤検知だけを狭く除外**していく。
- TypeScript のパスエイリアス等がある場合は、**ビルドと整合する解決**になるよう Knip 側にも反映する。

### 3.2 jscpd

- ルートに **jscpd 用の設定**を置く（JSON 等、公式に沿う形式）。
- 走査対象に少なくとも **`.ts` と `.astro`** を含める（プロジェクトに `.tsx` があれば含める）。
- **`dist/` や生成物ディレクトリは除外**する。
- **トークン閾値は最初は緩め**にし、ノイズが収まったら段階的に厳しくする。

### 3.3 誤検知への向き合い方

- レポートは機械推論であり、**削減や削除は常に人間が最終判断**する。
- 意図的な重複やツールが解釈できないパターンは、**設定で明示的に許容**し、可能なら理由をコメントまたは本ドキュメント近辺に短く残す。
- 「`verify` を常にゼロ exit」が目的ではなく、**チーム（本プロジェクトでは Kazki）が許容できる状態に収束させる**ことが目的。

## 4. npm scripts（Bun）

### 4.1 要求

- **`verify`（仮称、実装時に名前確定）**: 次を **この順で**実行し、**いずれかが非ゼロなら全体を失敗**とする。  
  1. 既存の **`astro check`** と同等の型／テンプレート検査  
  2. Knip  
  3. jscpd  

- **個別実行用**: `knip` と jscpd 相当を **別 script としても生やす**。設定調整や片方だけの再実行を容易にする。

### 4.2 メンテナンス

- Astro のエントリやディレクトリ構成を変えたら **`verify` を実行**し、Knip／jscpd の設定を**必要最小限**更新する。
- ツールのメジャーアップ時はリリースノートを確認し、**設定キー・CLI 互換**に注意する。
