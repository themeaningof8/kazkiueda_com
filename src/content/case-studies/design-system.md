> **このケースは何を示すか**: 守らせる規約ではなく「守られる」規約への再設計。保険・金融 2 事業で、デザインから実装までのリードタイムを約 5 日 → 3 日に短縮し、デザイナー以外のメンバーも Figma で施策を考える状態をつくった、意思決定と運用の記録。

## 問題の輪郭

**守られないガイドラインは、存在しないのと同じコストを払う。** むしろ、守られないことへのレビュー・修正・作り直しで、払っているコストは増えていく。

各事業にはデザインガイドラインがあった。ただ、それらはテキストとイラストで書かれ、最終的な運用は人の解釈に依存していた。デザイナーが仕組みで解くことに慣れていなかったこともあり、ルールは振り返りのたびに追加されていった。結果、運用歴が進むほどガイドラインは厚く、遵守は難しくなり、デリバリーのリードタイムを延ばす構造ができあがっていた。

CSS も同じ状態だった。コーディングガイドラインは存在していたが、当時の BEM 運用はきちんと守られないとスコープがないゆえの他パーツへの影響が残り続け、時限爆弾のように積み上がっていた。

Lead として私がやりたかったのは、「完璧だが遅いルール」ではなく、事業のデリバリー速度とエラー率に効くルールをつくることだった。

## 守らせる運用から、守られる運用へ

最初に考えたのは「どうすればルールを薄くできるか」。規約で速度を担保する、つまり Rails Way のように「規約に従えば早く作れる」世界観を、デザインとフロントエンドの両方に持ち込めないか、という問いから始めた。

## 三層の構造: Lint × TailwindCSS × UI ライブラリ

設計の核は 3 つの層を重ねることだった。

- **Lint**: 違反の自動検知。ESLint / Biome によって、コードの書き方と a11y の違反をコミット前に止める
- **TailwindCSS**: 選択肢の構造的制約。使えるユーティリティクラスを限定することで、「何を選ぶか」を都度考えさせない
- **UI ライブラリ**: 再発明の禁止。同じ見た目のパーツを各プロジェクトで再定義させない

なぜ 3 層かというと、**違反を止める層・選択肢を減らす層・実装そのものを共有する層** をそれぞれ分けたかったからだ。1 つの層だけに寄せると、どこかが抜ける。Lint だけでは選択肢は減らない。Tailwind だけでは複雑なコンポーネントの再発明は止まらない。UI ライブラリだけでは使う側の書き方を矯正できない。

Tailwind の社内事例は当時少なく、採用には躊躇もあった。ただ、社内の CSS 設計の運用状況を見た上で「スコープの不在こそが事故の主因」と判断し、「HTML と CSS が同じ場所で書かれ、影響範囲がカプセル化される」という Tailwind の特性が一番効くはずだと決めた。結果として、事業内で先行採用し、他チームに展開される足場になった。

UI ライブラリは React プロジェクトから、10 前後のコンポーネントで始めた。再発明を防ぐだけでなく、**ジュニアデザイナーでも一定水準の UI を組み立てられる** ことを目指した。

### トークンパイプライン: Figma と実装の翻訳をなくす

同じ考え方をデザインプロセスにも持ち込んだ。Figma Variables を Single Source of Truth とし、`tokens.json` を経由して TailwindCSS に自動変換するパイプラインを Style Dictionary で実装した。

代替案として Tokens Studio プラグイン、手運用での同期、Figma Styles のみで完結する運用も検討したが、(1) デザイナーとエンジニアの間で「色はこれです」という翻訳工程がどうしても残る、(2) 値の変更履歴が追いにくい、という 2 点から退けた。Style Dictionary は出力先を増やせるので、将来的に iOS / Android にも同じトークンを供給できる余地を残した。

実装の詳細は [Qiita のアドベントカレンダー](https://qiita.com/themeaningof8/items/f779ed2af011b82ea3f4) に書いた。

### アクセシビリティを土台に据える

アクセシビリティは、きちんと対応しようとすると工数がかかり、売上に直結しにくいから優先度が上がらず、後回しにされ続ける。よくある構造問題だ。

この構造にルールで立ち向かうのは現実的でないと判断した。かわりに、**UI ライブラリの層でデフォルトとして組み込んだ。** 使う側が意識しなくても、Button / Dialog / Form のコンポーネントを使えば、キーボード操作とフォーカス管理と ARIA 属性が最低限担保される。

劇的な改善ではない。ただ、「気づいたらできていた」という状態を作ることに意味があった。QA の指摘、新規参画者の学習、将来の法務対応 — これら複数のコストを、コンポーネント層に寄せることで同時に下げられた。

## 議論を減らすカラー設計

カラーも同じ問題を抱えていた。デザインレビューで「なぜこの色なのか」の根拠が、人によってずれる。自前スケール、Material Color、Tailwind 標準パレットも検討したが、**各ステップに意味が定義されている** 点で Radix Colors の 12 段階スケールを採用した。「この色にした理由は？」という議論が、パレットの選定段階で完結するようになる。

## 共通ライブラリから、コピー前提の分離へ — 保守責任の再設計

このケース最大の意思決定は、保険事業に入る前の金融事業での経験から来ている。

金融事業では、私が提唱した三層の構造を同僚に引き継ぎ、共通 UI ライブラリを中央のリポジトリで管理する形で運用していた。そこで見えたのが、**ライブラリ側の修正待ちが事業側の実装をブロックする** という現象だった。ライブラリに 1 行直せば済む修正も、プロジェクト間の優先度調整とリリースサイクルを経るため、事業側の進行が止まる日が出てくる。

さらに、共通リポジトリでの管理は全プロジェクトが均等に保守される前提に立っている。ところが実際には、非注力サービスはどうしても生まれるし、そこには同じだけの保守コストを割けない。保守されないサービスでライブラリが壊れ、他サービスへの影響が波及する。

この 2 つの観察から、**共通リポジトリモデルそのものが、私たちの組織規模と事業ポートフォリオには適合していない** と判断した。

保険事業では設計思想を変えた。UI ライブラリを「インポートする依存物」ではなく、**Storybook から各プロジェクトにソースコードをコピーする実装物** として扱う。バージョン依存が消え、プロジェクト間の結合が切れる。各プロジェクトは自分が使うコンポーネントの最終的な責任を持つ。

shadcn/ui を採用したのは、この「依存を持たない」アプローチが、私が必要としていた保守責任の分界と完全に一致していたからだ。

この方針転換は、エンジニアリングマネージャー / テックリードと、同僚のデザイナー / デザインマネージャーとの合意形成を経て決めた。「共通ライブラリをやめる」というのは一見後退に見えるので、(a) ライブラリ修正待ちがブロッカーになっていた事実、(b) 非注力サービスで保守歪みが起きていた事実、を具体例として示した上で、「保守責任を中央集権から分散させる」ことの利点を握ってもらった。

## 起きた変化

- **デザインから実装までのリードタイム**: 約 5 日 → 約 3 日（週次換算で約 40% 削減）
- **A/B テストの回転数が上がった**: サイクル短縮によって、同じ期間で試せる実験の数が増えた
- **機能 / 施策のリリース数が増えた**: 同じ開発リソースで、より多くの施策が事業側に届くようになった
- **デザイナー以外のメンバーが Figma で施策を考えるようになった**: これが最も大きな変化だと思っている。デザインの意思決定の入り口が広がり、「デザイナーに頼まないと見えない」状態が崩れた。結果として、上流の議論の密度そのものが変わった

チーム全体として、実装の細部ではなく体験と仕様の議論に時間を使えるようになった。

## 学んだこと、次ならこうする

規約とルールをベースに設計した結果、「規約が厳しくて窮屈」という不満がデザイナーから出たのは事実として受け止めている。例外を許しにくく、イマジネーションが発揮しにくいという指摘は、構造的に正しい。

ここから次に同じ仕事を任されたら、**起点を変える** だろう。規約やシステムの設計から入るのではなく、「誰の、何を改善して、どのような成果を出すのか」から始める。デザインシステムは目的ではなく手段で、規約はさらにその手段の手段でしかない。もし規約の厳しさが成果の阻害要因になるなら、そのときはアプローチを変える。システムを守るために成果を犠牲にしない、という順序を最初から明確にしたい。

プリミティブな UI の組み合わせに関する知識の必要性も、次の課題として残っている。コンポーネントをコピーで配る設計にしたぶん、組み立て側のリテラシーに依存する部分が増えた。ここは規約ではなくドキュメントと Storybook の設計で引き上げるべき領域だと考えている。
