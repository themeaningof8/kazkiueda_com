## 問題の輪郭

> **成果要約**: Lint・Tailwind・UIライブラリとトークンパイプラインの整備により、意匠解釈のすり合わせ時間を週次換算で約40%削減。UI再実装コストを体感で半減させ、チーム全体の議論を実装の細部からUX・仕様の話へシフトしました。

今までも各事業でデザインガイドラインはありましたが、これらはテキスト・イラストベースかつ解釈を大きく含むものでした。デザイナー全体の課題感として、どうしても仕組みで解決することが苦手であるというところがあり、これが振り返りの際のルールの追加による対策に集中していたために、運用歴が進めば進むほど、複雑で遵守が困難なガイドラインが出来上がり、結果としてこれが施策のデリバリータイムが上がらない仕組みを作ってしまっていました。

これは、CSSも同じくコーディングガイドラインというものを持っていたのですが、当時採用していたBEMはきちんと運用すれば問題ないのかもしれませんが、きちんと運用されないとCSS特有のスコープがないことによる他のパーツへの影響を気にする必要があり、これが時限爆弾のようになっていました。

## 「守らせる」ではなく「守られる」状態を目指す

まず考えたのは「どうやったらルールを薄くできるか？」です。私がやりたかったのは開発スピード向上、エラー率の減少による事業への貢献です。そのためには、「完璧だけど非常に遅いルール」では意味がありません。その時に Rails Way のような「規約に従えば早く作れる」という世界観を作れないかなと模索し始めました。

## 三層の構造

まずリントルール。ESLint や Biome で、コードの書き方そのものに制約を持たせました。CSS や a11y など、規約として自動的に違反を知らせることができる仕組みを取り入れようと考えました。

次に TailwindCSS によるスタイルの絞り込み。使えるユーティリティクラスを構造的に限定することで、「何を使っていいか」を都度考えなくても、選択肢が自然に絞られます。当時はあまり社内に事例がありませんでしたが、私が社内で初めて事業に入れたことで、うまくいくだろうと思っていました。一番効果があるだろうと思ったのは CSS と HTML が一緒になることで、影響範囲をカプセル化し、またそのHTMLタグにあたっているスタイルを明示できることでした。

3つ目が React を使用するプロジェクトへのUIライブラリ。最初は10程度のライブラリからスタートしましたが、これによって同じ見た目のパーツが何個も再発明されなくなることを期待しました。また、スクラッチで複雑な実装をしなくてもジュニアのデザイナーが実装できるものを目指しました。

### トークンパイプライン

デザインプロセス側にも同じ考え方を持ち込みました。Figma Variables を Single Source of Truth として、`tokens.json` 経由で TailwindCSS に自動変換するパイプラインを Style Dictionary で実装しています。Figma とコードで同じトークンが使われる状態を担保することで、デザイナーとエンジニアの間で「翻訳」が発生しなくなります。詳細は [Qiita のアドベントカレンダー](https://qiita.com/themeaningof8/items/f779ed2af011b82ea3f4) に書きました。

### アクセシビリティを土台に

アクセシビリティへの対応は、ずっと気になっていたテーマでした。ただ、きちんと対応しようとすると工数がかかります。売上に直結しにくいから優先度が上がらず、後回しにされ続ける。これはよくある構造だと思います。

UI ライブラリを構築するなら、コンポーネントの段階で a11y 対応を組み込めると思いました。、意識しなくても一定の水準が保たれます。劇的な改善ではないけれど、「気づいたらできていた」という状態を作ることに意味があると感じていました。

## 金融事業での先行と、そこで見えた限界

保険事業のデザインシステムに入る前に、金融事業で先行して取り組んでいたデザインシステムの開発。私は前述のような概念をメンバーに伝え分社による転籍をし、後はメンバーに実装・運用してもらっていましたが、その中で新たな問題や気づきがありました。それはUIライブラリの保守コストがバカにならないということです。

さらに問題だったのが、非注力サービスの扱いです。事業の中でどうしても優先度の低いサービスは生まれます。共通リポジトリで管理するモデルは、全プロジェクトが均等に保守される前提に立っています。しかし、事業の現場では同じように各サービスの保守コストが当てられるわけではありません。この辺りは作って初めてわかったことで、のちの保険事業でのUIライブラリの設計の際に非常に参考になりました。

### 保険事業での方針転換

この経験を踏まえて、保険事業では設計の考え方を変えました。

インポートではなく、ソースコードのコピーで対応する方式にしました。つまりUIライブラリを自作するのではなく、必要に応じてStorybookから各プロジェクトにコンポーネントをコピーする形です。バージョン管理の依存がなくなるので、どこかのプロジェクトの状態が他に影響しません。shadcn/ui を採用したのも、この設計思想と一致していたからです。コンポーネントをコピーして使うという shadcn/ui のアプローチは、最初から「依存を持たない」ことを前提にしています。

## カラーに根拠を持たせる

カラー設計にも同じ問題がありました。デザインレビューの際に「なぜこの色なのか」という根拠が人によって違う。Radix Colors の12段階スケールを採用したのは、各ステップに意味が定義されているからです。何にどの色をつけるかが明確になると、「この色にした理由は？」という議論が自然に減っていきます。

## 変わったこと、変わらなかったこと

### 変わったこと

- Figmaのコンポーネントを使った初期モックデザイン、デザインレビューの打ち返しが減り、週次換算で約40%ほど工数が減りました
- コンポーネント再利用により、施策ごとの再実装コストが体感で半減しました
- デザイナー以外のメンバーも、Figma のUIコンポーネントを使って施策を考えるようになりました

チーム全体で、実装の細かい話より体験や仕様の議論に時間を使えるようになったのが、一番大きな変化だったと思います。

### 変わらなかったこと・学んだこと

残念ながら事業の売却により、1年足らずで他社に承継されました。
難しかったのはプリミティブなUIの組み合わせもまた知識が必要で、素人が作るとよくわからないUIになってしまったり、実装可能性を無視した機能になってしまうことでした。

また、これはデザイナー側の意見として次は考慮したいこととして、規約が厳しすぎて不満の声が出たことが挙げられます。規約ベースだと例外が許されず、デザイナーにとってイマジネーションが発揮しにくいのも事実なようです。
